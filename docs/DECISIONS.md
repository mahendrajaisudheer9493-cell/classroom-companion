# Decisions

Changes to or clarifications of docs/DESIGN.md. One line each: date · decision · why.

- 2026-11-17 · Prisma pinned to 6.x (6.19.3), not 7+ · Prisma 7 removes `url`/`directUrl` from schema.prisma; 6.x keeps the documented Supabase pooled + direct URL setup.
- 2026-11-17 · `@types/node` ^22 (scaffold had ^20) · vitest 5 requires it; local Node is 22.
- 2026-11-17 · TypeScript target ES2020 (scaffold had ES2017) · Telegram IDs are BigInt and BigInt literals need ES2020.
- 2026-11-17 · `typecheck` runs `next typegen` before `tsc --noEmit` · Next 16 generates route types such as `LayoutProps`; without them tsc fails on a clean checkout.
- 2026-11-17 · Env is validated lazily via `getEnv()`, not at import; the seed validates only `SEED_*` vars · `next build`, tests and seeding work without every secret filled in.
- 2026-11-17 · Membership's unique key has nullable classId/subject, and Postgres treats NULLs as distinct · code finds-or-creates memberships instead of relying on the constraint for coordinator/class-teacher rows.
- 2026-11-17 · Seeded users have `chatId` null until they send /start · Telegram only lets a bot message users who started it.
- 2026-11-17 · `/api/health` calls `connection()` · `cacheComponents` is on in next.config; this guarantees the DB check runs per request, never at build.
- 2026-11-17 · `canViewStudentAssignment` returns "full" for the class teacher; read-only is enforced because every action also requires `canManageClassSubject` · keeps one "what can I see" answer and one "what can I do" answer.
- 2026-11-17 · Unknown class → 404, someone else's class → 403 · existence of a class id isn't sensitive; the 403 is what the access demo shows.
- 2026-11-17 · A Telegram user with no membership and no linked student counts as "not linked" for the Mini App (401 not_linked) · the bot creates a User row on first contact, before they join anything.
- 2026-11-17 · ProcessedUpdate is inserted with `createMany({ skipDuplicates: true })` before handling · a retry is skipped without a noisy P2002 error log; if the handler then fails, the error boundary replies "Something went wrong" and Telegram does not retry (the user taps again).
- 2026-11-17 · Join-flow buttons carry the join code id (`pk:<joinCodeId>:<studentId>`, 54 bytes) and every tap re-checks code validity, class and claim on the server · stale or forged buttons can't link to another class.
- 2026-11-17 · Seed adds a one-use teacher invite `GFSCI8A` (Science teacher, 8A, 30 days) · lets the `t_<CODE>` flow be tested without an invite UI yet.
- 2026-11-17 · The bot overwrites `User.displayName` with the Telegram name on every update (per task spec) · rosters always show `Student.name`, so a student's identity never comes from Telegram.
- 2026-11-17 · Mini App pages are client components that fetch `/api/app/*`; the class page wraps its `useParams` client component in `<Suspense>` · with `cacheComponents` the shell is prerendered and all data stays behind the initData-checked API.
- 2026-11-17 · telegram-web-app.js loads with the default `afterInteractive` strategy in `app/app/layout.tsx`; `apiFetch` waits for `window.Telegram.WebApp` · `beforeInteractive` is only allowed in the root layout.
- 2026-11-17 · Roster shows which Telegram account claimed each name (`linkedAs`) · lets a teacher spot a wrong claim before unlinking.
- 2026-11-17 · Class page has a [Share] button (Telegram share sheet) next to [Copy link] · teachers usually post the link into the class group.
- 2026-11-17 · State machine also allows NEEDS_REVISION → BLOCKED (student stuck on a redo); ACKNOWLEDGE from any state after ASSIGNED keeps the status · DESIGN §4 needs stuck on a revision and re-acknowledging a change without losing progress.
- 2026-11-17 · LLM calls use forced `tool_choice` on Claude Haiku 5.5 (accepted on this model; it skips thinking for the forced call), no `temperature` (non-default values 400 on Haiku 5.5), one retry on network errors only, `maxRetries: 0` in the SDK · predictable latency under the 8 s budget; timeouts fall back to buttons/form immediately.
- 2026-11-17 · The teacher-parse prompt includes a 15-day calendar with weekdays · date arithmetic is the model's weakest spot; giving it the calendar turns "day after"/"Monday" into a lookup.
- 2026-11-17 · Known ambiguity: "next Friday" sometimes resolves to the Friday of next week (eval case 8) · genuinely ambiguous in Indian English; safe because the teacher always sees the exact date in the preview before [Send].
- 2026-11-17 · sendDue claims each row by moving its `sendAfter` 2 minutes ahead (conditional update) before sending · tick and webhook can run sendDue at once without double sends and without a SENDING status; a crash mid-send retries after 2 minutes.
- 2026-11-17 · Telegram 400 (e.g. chat not found) is DEAD like 403, not retried · a bad request won't succeed on retry; 429 honours retry_after; other errors back off 2^attempts minutes, DEAD after 6.
- 2026-11-17 · Outbound payload carries `meta { assignmentId, studentAssignmentId }` · side effects on send (deliveredAt) and cleanup on cancel without extra columns.
- 2026-11-17 · JobLease is taken with one `INSERT … ON CONFLICT DO UPDATE … WHERE lockedUntil < now` and released at the end of the tick · atomic, no overlapping ticks, self-heals after 55 s if a tick dies.
- 2026-11-17 · While questions are open (class, date, time), the partial draft lives in a PendingAction; the DRAFT Assignment row is created once class + due time are known · Assignment.classId and dueAt are required columns; the preview (and "Edit in app") always points at a complete draft.
- 2026-11-17 · Typed answers ("tomorrow 5pm", "4pm") are parsed by code (`parseDueText`, `parseClock`), not the model; a long message while a question is open is treated as a new request · deterministic, instant, and a bare "4" is rejected as ambiguous.
- 2026-11-17 · "Both" creates one draft (and one preview with its own [Send]) per class · each class is its own assignment with its own roster and status.
- 2026-11-17 · On a change, students who already received the card get "Updated: …"; students who never received it (unlinked/queued) get the new version of the card instead · nobody gets an update about something they never saw.
- 2026-11-17 · On cancel, only students who received the card are told; unsent cards/updates/reminders are dropped · no "Cancelled" for work a student never saw.
- 2026-11-17 · AccessDenied thrown inside a bot handler is answered with its message and logged as access.denied (not "Something went wrong") · the user learns why; the log shows the attempt.
- 2026-11-17 · The student-interpretation prompt defines confidence as being about the intent only; an unclear assignment is expressed as `assignmentId: null` · first eval run had the right intent 18/18 but low confidence on "ok"/"half done" because the homework wasn't named; code already asks "Which homework?" for that.
- 2026-11-17 · `npm run eval` counts a case as failed when confidence is below the threshold, since the bot would ask instead of acting · the eval measures what the student actually experiences.
- 2026-11-17 · A user with both roles: any SUBJECT_TEACHER membership → typed text goes to teacher parsing; otherwise a linked student → student handling (photos/files likewise go to student handling only for non-teachers) · one predictable rule; a teacher testing as a student uses a separate Telegram account.
- 2026-11-17 · LLM candidate ids for students are StudentAssignment ids (not Assignment ids) · the id the model returns is exactly what the action needs, and it can only be one of the student's own rows.
- 2026-11-17 · [I'm stuck] alerts the teacher immediately ("no details yet"); typed details within 30 min go as a short follow-up ("added about …") · the teacher hears about a block at once; details aren't lost. Known limitation: any text typed in that window is taken as the details (student can tap [Skip]).
- 2026-11-17 · Alert dedupe keys: `doubt:<doubtMessageId>`, `stuck:<saId>:<blockedAt>`, `still:<saId>:<blockedAt>` (per teacher) · one alert per doubt and per blocked episode, even on double taps or retries.
- 2026-11-17 · Direct student buttons (stk/don/inc/sst/fig/ist/prg) carry the StudentAssignment id and re-check status, so repeats are no-ops; stateful ones (confirm, which, ask, skip, file) use a one-time PendingAction → "This option has expired." on reuse.
- 2026-11-17 · A repeated "bringing it to class" or identical typed text is treated like a duplicate file: "Already received ✓", no new Submission · a double tap never creates two submissions.
- 2026-11-17 · Silent also lists students who haven't seen a change and students not on Telegram yet, each with a tag · both mean "this student doesn't know"; the teacher acts on them the same way (nudge / talk in class).
- 2026-11-17 · [Mark resolved] is offered only for BLOCKED students; an unanswered question leaves the Stuck list when the teacher replies · resolving a question without answering it would hide it.
- 2026-11-17 · [Run reminders now] and the cron share `runTickWithLease()` · same code path and the same lease, so pressing it during a cron tick never double-sends.
- 2026-11-17 · Nudge dedupeKey `nudge:<saId>:<IST date>`; submitted/completed/unlinked students are skipped and counted · at most one nudge per student per assignment per day.
- 2026-11-17 · The Telegram BackButton is used inside Telegram; a plain "‹ Back" link appears only in a normal browser · native navigation without a duplicate on-screen control.
- 2026-11-17 · One endpoint `POST /api/app/doubts/:saId/message` serves both sides: the owning student adds a doubt (teacher alerted), the subject teacher replies (queued, quiet hours) · one thread, one write path; everyone else gets 403.
- 2026-11-17 · Queued teacher replies show "will be delivered at 7:00 am" in the thread, read from the pending OutboundMessage · the teacher sees exactly what the queue will do.
- 2026-11-17 · Files are previewed by fetching `/api/files/:id` with the initData header and showing a blob URL · `<img src>` can't send the auth header, and the Telegram file URL (with the bot token) never reaches the browser.
- 2026-11-17 · "Needs revision" requires a comment; "Completed" may be empty · a student must know what to redo.
- 2026-11-17 · Mini App uploads (≤ 4 MB) are sent by the bot to the student's own chat (caption "Your submission for …") to get a Telegram file_id, then go through the same `submitWork` · files stay in Telegram; the student also sees what they handed in. 4 MB stays under Vercel's request body limit.
- 2026-11-17 · "My work" groups: Overdue (past due, not submitted) · Due today · This week (7 days) · Later · Done (submitted or completed); cancelled assignments disappear · matches S8; Done includes SUBMITTED so the open lists only show what still needs doing.
- 2026-11-17 · "Updated" note on the work page is built from the latest `assignment.updated` event (old → new due) · no extra columns; days when the date moved, times when only the time moved.
- 2026-11-17 · Reminder rules are a pure function (`computeDueReminders(now, rows, settings)`); the tick and [Run reminders now] share `runReminders` · every rule is unit-tested with a fixed clock; one code path (T9).
- 2026-11-17 · Reminders are evaluated only outside student quiet hours, not queued for 07:00 · nothing piles up overnight; at 07:00 the next tick fires what's due.
- 2026-11-17 · ReminderFired rows and the student's single outbound message are written in one transaction; reminder keys already fired are filtered out before any wording work · a crash can't record a reminder without its message, and reruns never double-send or re-call the model (SYS2).
- 2026-11-17 · Blocked check-in = first 07:00 IST at least an hour after blockedAt (or `BLOCKED_CHECKIN_AFTER_MINUTES`); key includes blockedAt · "the next morning", once per stuck episode, without a 1-minute check-in for someone stuck at 06:59.
- 2026-11-17 · No "did you see it?" once the deadline has passed · the overdue reminder covers it, and "Due Thu" in the past reads wrong.
- 2026-11-17 · Due texts are relative ("tomorrow at 8:00 am", "yesterday at 8:00 am", "on Mon 9 Nov at …") and computed by code · correct whatever day the reminder actually fires.
- 2026-11-17 · `reminder.sent` is logged when the queue actually sends the message (from payload meta), not when it's queued · the log means "the student got it".
- 2026-11-17 · [Run reminders now] names only the teacher's own students; reminders for other classes are counted · the tick is global, its result must not leak names across classes. "skippedBlocked" = linked stuck students whose submit reminders are held.
- 2026-11-17 · Merged reminder messages carry no single assignmentId, so cancelling an assignment doesn't drop them · they are queued and sent in the same tick outside quiet hours, so the window is seconds.
- 2026-11-17 · Reminder wording: the model writes single reminders only (merged ones use the template), with a 4 s timeout, at most 20 model calls per tick run in parallel; output checked (≤ 400 chars, no links, contains the title, no other student's first or full name from the class roster) else template + `model.failure` · keeps the tick inside 60 s on a 07:00 burst; buttons and due texts always come from code.
- 2026-11-17 · Digest counts = `computeTriage` counts + "haven't seen a change" (the tagged part of Silent), so the digest always matches the board · one source of truth for every number (T5).
- 2026-11-17 · Digest fires from DIGEST_TIME for 3 hours, once per teacher per IST date (outbound dedupeKey `digest:<userId>:<date>`); the key is checked before computing counts · a missed tick still sends it, an afternoon deploy doesn't send "Good morning!", and no triage queries run after it's sent.
- 2026-11-17 · Digest text is a code template (no model) · the numbers are the message; nothing for the model to add.
- 2026-11-17 · [Send my digest now] uses a timestamped dedupeKey and says so when all counts are zero instead of sending · repeatable for demos, and shows the skip rule.
- 2026-11-17 · Homework picking for done/submission/progress messages and photos: the model's valid id → the only open one → the only one not yet SUBMITTED/COMPLETED (NEEDS_REVISION counts as still to do) → ask, with still-to-do work listed first · students kept being asked "Which homework?" when only one was left to hand in; every reply names the homework, so an auto-pick is visible and the confirm step still applies.
